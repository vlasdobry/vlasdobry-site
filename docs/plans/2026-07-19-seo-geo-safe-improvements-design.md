# Безопасные SEO/GEO-улучшения vlasdobry.ru — дизайн

**Дата:** 2026-07-19  
**Основание:** проверенный SEO/GEO-аудит production-сайта от 2026-07-19  
**Статус:** одобрено пользователем 2026-07-19

## Цель

Устранить подтверждённые технические и контентные SEO/GEO-проблемы, улучшить загрузку страниц и связность сущности автора, не меняя визуальный дизайн, рабочую маршрутизацию, анимацию главной и поведение диагностических инструментов.

## Ограничения безопасности

- Не менять сетку, типографическую систему, цветовую схему, анимацию `hero ↔ landing` и пользовательские сценарии.
- Не смешивать работу с существующими незакоммиченными файлами и локальными экспериментами.
- Сохранить имеющуюся незакоммиченную правку CSP для `wss://mc.yandex.ru` при подготовке итоговой конфигурации.
- Не включать SSG/SSR-миграцию в первый релиз: это отдельная архитектурная задача.
- Не отправлять изменения в production до прохождения typecheck, build, smoke, SEO-регрессий и визуального сравнения.
- Все утверждения в GEO-контенте должны иметь проверяемое основание в официальной документации или первичном исследовании.

## Выбранный подход

Выбран консервативный поэтапный вариант:

1. Изолировать работу в отдельной ветке и worktree.
2. Зафиксировать технический и визуальный baseline.
3. Создать регрессионные проверки до исправлений.
4. Исправлять корневые причины небольшими атомарными изменениями.
5. После каждого блока повторять проверки.
6. Рассматривать SSG/SSR только после стабилизации низкорисковых изменений.

Отвергнуты два альтернативных подхода:

- единый большой релиз — слишком широкий радиус возможной регрессии;
- немедленная SSG/SSR-миграция — максимальный риск для текущей SPA-архитектуры и анимаций.

## Архитектура изменений

### 1. Генератор двуязычного блога

Текущая генерация sitemap строится только по русскому массиву статей и предполагает одинаковый slug для RU и EN. Это нарушается у PMax-статьи: русский slug — `pmax-vs-search-lokalnyi-biznes`, английский — `pmax-vs-search-local-business`.

Генератор должен формировать языковую пару по каталогу контента, а URL брать из frontmatter каждой локали. Один объект пары содержит RU- и EN-версию. Из него генерируются:

- отдельные канонические URL;
- взаимные `hreflang` и `x-default`;
- две корректные записи sitemap;
- корректные ссылки в `llms.txt` и `llms-full.txt`.

Первый Markdown-H1 статьи удаляется из HTML тела при генерации, поскольку заголовок уже отображается шаблоном `BlogPost` и статическим fallback. Это устраняет два H1 без изменения основного визуального заголовка.

### 2. Регрессионный контроль SEO

Добавляется локальный скрипт проверки production-сборки. Он должен завершаться ошибкой, если:

- у страницы статьи не один H1;
- canonical или hreflang не соответствуют маршруту;
- языковые ссылки не взаимны;
- sitemap содержит несуществующий PMax-slug;
- `llms.txt` или `llms-full.txt` содержат старую ссылку;
- JSON-LD не разбирается как JSON;
- обязательный маршрут отсутствует в `dist`.

Проверка включается в общий `npm run check` после сборки и до smoke-тестов.

### 3. CSP и серверная доставка

В `nginx.conf` сохраняется `wss://mc.yandex.ru` и добавляются только реально используемые домены Метрики `https://mc.yandex.com` в необходимые директивы. После сборки проверяется отсутствие заблокированных запросов Метрики и сохранность доступа к Health Score proxy.

Для текстовых ресурсов включается gzip. Для `blog-data.json` и будущих JSON-индексов задаётся кэширование, допускающее обновление контента. Хешированные JS/CSS продолжают получать длительный immutable-кэш.

### 4. Пиксельно-нейтральная производительность

Изображения автора в элементах 96×96 переводятся на существующую лёгкую WebP-версию при сохранении размеров, `object-fit`, скругления и альтернативного текста.

Полный `blog-data.json` не должен загружаться на каждой статье. Безопасная целевая схема:

- компактный локализованный индекс содержит метаданные для списка и связанных статей;
- отдельный JSON статьи содержит HTML, FAQ, TL;DR и TOC;
- `BlogPost` загружает только текущую статью и компактный индекс.

Изменение принимается только при идентичном пользовательском содержимом и прохождении визуального сравнения.

### 5. Граф сущности и GEO-контент

Структурированные данные формируются как связный граф со стабильными идентификаторами:

- `https://vlasdobry.ru/#website` для `WebSite`;
- `https://vlasdobry.ru/#person` для `Person`;
- Article ссылается на автора и издателя через `@id`.

Страницы About получают соответствующие Person/OG-данные. Разметка не должна заявлять факты, отсутствующие в видимом тексте.

В GEO-материалах корректируются только проверенные устаревшие утверждения:

- `llms.txt` описывается как экспериментальный формат, а не официальный фактор ранжирования;
- FAQ отделяется как формат полезного контента от доступности Google FAQ rich results;
- удаляются неподтверждённые проценты, гарантированные сроки и заявления о специальном чтении AI-системами;
- дата изменения обновляется только при содержательной правке.

## Поток данных

1. Markdown каждой локали читается отдельно.
2. Локализованные статьи объединяются в пары на уровне каталога.
3. Из пары формируются URL, sitemap, hreflang и LLM-индексы.
4. Сборка создаёт компактные индексы и отдельные payload-файлы статей.
5. Страница получает локализованный payload по текущему URL.
6. React отображает тот же интерфейс, что и до изменения.

## Обработка ошибок

- Отсутствующая локаль не должна порождать выдуманный alternate URL.
- Дублированный slug внутри одной локали останавливает сборку.
- Некорректный frontmatter или JSON-LD останавливает quality gate.
- Ошибка загрузки статьи сохраняет текущий экран «не найдено» и не ломает список блога.
- Любое расхождение визуальных снимков проверяется вручную; автоматическое принятие широкого diff запрещено.

## Проверка

До и после изменений проверяются:

- `npm run typecheck`, production build, SEO regression и smoke;
- главная RU/EN, услуги SEO/GEO, список блога, RU/EN PMax-статья, About и 404;
- мобильные и десктопные снимки;
- переход `hero ↔ landing`, язык, FAQ, Health Score и CTA;
- консоль браузера, CSP и сетевые запросы;
- Lighthouse на одинаковом окружении, без требования улучшить оценку ценой скрытия контента.

Допустимые визуальные изменения ограничены удалением повторного заголовка статьи и переносами строк, вызванными фактологически необходимой правкой текста. Все остальные страницы должны сохранить текущий вид.

## Граница первого релиза

В первый релиз входят генератор URL, SEO-регрессии, H1, CSP, gzip, лёгкие изображения, разделение blog-data, связный JSON-LD и фактологические правки при наличии успешного визуального контроля.

SSG/SSR, переработка cookie-баннера и крупное разбиение общего JS-бандла требуют отдельного дизайна после измерения эффекта первого релиза.
